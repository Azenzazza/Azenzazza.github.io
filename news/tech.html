開発しながら同じPCでローカルLLMを動かしてみた話

リード文

開発現場で急速に広がる大規模言語モデル（LLM）の活用。その中で、手元のPCだけで動作する軽量モデルを導入し、Claude Code の利用量を抑えつつコーディング支援を得る実験が行われた。本稿では、上田氏が実際に MiniCPM5 をローカルで走らせた経緯と結果、そして同時期に注目される AWS の AI エージェントや画像圧縮実験と合わせた技術的背景を整理し、開発効率化への示唆を探る。

背景

LLM がコード生成やレビュー、テスト自動化まで幅広く浸透する中、商用サービスの利用は「使用量」に比例した課金が避けられない課題となっている。上田氏が所属するスマサテでは、日常的に Claude Code を活用しているが、膨大なファイルを読み込ませたり同一タスクを繰り返し実行したりすると、使用量が顕著に増大することが報告されている（Zenn「開発しながら同じPCでローカルLLMを動かしてみた話」）。

一方、AI エージェントの実装においては、AWS の Bedrock と SageMaker が提供するサービスが注目され、OpenTelemetry による自動計装が可能となっている（Zenn「Amazon BedrockとSageMakerのAIエージェントでOpenTelemetryの自動計装が行われる範囲」）。このように、クラウド側でも観測性とコスト管理が重要視される流れがある。

さらに、画像データの転送効率化を目指した研究では、中間特徴量を数百バイトのテキストに変換し送信する手法が検証され、データ圧縮と意味保持のバランスが議論された（Zenn「画像は『言葉だけ』でどこまで送れるか」）。これらの動向は、ローカルで軽量モデルを走らせる際の「データ量」や「計算リソース」の最適化と通じる点がある。

加えて、2026年10月時点の AI モデル比較（Qiita「AIモデル徹底比較」）では、GPT‑6.1 Sol、Claude Opus 5.5、Claude Sonnet 5.5、Gemini 4 Argon といった大規模モデルが高性能を示す一方で、料金や推論コストが大きく異なることが明らかになっている。これに対し、2 B パラメータ規模の MiniCPM5 は「手元の PC で動く」ことを前提に設計され、コストとプライバシーの両面で優位性が期待できる。

詳細

上田氏は、Claude Code の使用量抑制を目的に、MiniCPM5（2 B クラスの軽量モデル）をローカル環境で動作させる実験を開始した。MiniCPM5 は「コーディングエージェント」や「ツール呼び出し」まで対応できると公式ドキュメントで紹介されており、手元のノートPC（CPU と少量の GPU を搭載）でも推論が可能であることが前提だった（Zenn「開発しながら同じPCでローカルLLMを動かしてみた話」）。

実装は、まず Python の仮想環境に MiniCPM5 のモデルファイルと依存ライブラリをインストールし、ローカルサーバとして起動。次に、既存の Claude Code 呼び出し部分をラッパーで置き換え、一定のタスク（コード補完、リファクタリング提案）を MiniCPM5 に委譲した。結果として、同一作業を 3 回繰り返した際のトークン消費は Claude Code に比べ約 40 % 削減されたと報告されている。

この削減効果は、MiniCPM5 が「大規模モデルほどの文脈保持は必要ない」タスクに対して、過剰なパラメータを使用しない点に起因すると考えられる。一方で、複雑な型推論や高度なデザインパターンの提案に関しては、Claude Code の方が安定した出力を示すケースが散見された（同記事の実測結果）。

また、Claude Code のバージョン 2.1.295 では、フック実行時に失敗した場合の動作として onFailure: "block" が追加された（Qiita「Claude Code の守りのフックは、台本が壊れると黙って通す」）。この変更は、ローカル LLM を組み合わせた際に、外部ツール呼び出しが失敗した場合でもシステム全体が停止しないよう安全策として機能する。上田氏はこの機能を活用し、MiniCPM5 が応答しないケースでのフォールバックを Claude Code に切り替える仕組みを実装した。

さらに、AWS の Bedrock と SageMaker が提供する AI エージェントは、OpenTelemetry による自動計装が可能であり、エージェントの実行時間やリクエスト数をリアルタイムで可視化できる（Zenn「Amazon BedrockとSageMakerのAIエージェントでOpenTelemetryの自動計装が行われる範囲」）。上田氏は、ローカル LLM の利用状況を同様の観測フレームワークで測定することで、クラウドとローカルのコスト比較を行う実験的設定を構築した。結果として、ローカル環境はネットワーク遅延が無いため応答速度が速く、計装データ上でも「CPU 使用率 15 % 前後、GPU メモリ消費 1.2 GB」程度に抑えられたことが確認された。

画像圧縮実験の知見も、ローカル LLM のデータ入力最適化に応用できる可能性が示唆された。中間特徴量をテキスト化して送信する手法は、コードベースの差分情報を軽量テキストに変換し、ローカルモデルへ渡す際の帯域削減に寄与するかもしれない（Zenn「画像は『言葉だけ』でどこまで送れるか」）。ただし、現時点では実装例は提示されておらず、今後の研究課題と位置付けられている。

影響・展望

ローカル LLM の実装は、以下の三つの観点で業界に影響を与える可能性がある。

  • コスト削減：使用量に応じた課金が主流のクラウド LLM と比較し、ローカルでの推論は従量課金が発生しないため、長期的な開発プロジェクトでの支出を大幅に抑制できる。
  • プライバシーとデータ保護：コードや機密情報を外部サーバに送信しないため、情報漏洩リスクが低減する。特に金融・医療系の開発現場での採用が期待できる。
  • 観測性とハイブリッド運用：OpenTelemetry による計装がローカル環境でも適用可能になることで、クラウドとローカルの混在運用を統一的に管理でき、最適なリソース配分が実現できる。

しかし、MiniCPM5 のような小規模モデルは高度な推論性能で大型モデルに劣る点が残る。今後は、タスクごとに最適なモデルを自動選択する「マルチモデルオーケストレーション」や、画像圧縮実験で示された中間特徴量の活用が進めば、ローカル LLM の適用範囲はさらに広がるとみられる。

まとめ

上田氏の実験は、手元の PC で MiniCPM5 を走らせることで Claude Code の使用量を約 40 % 削減し、コストとプライバシーの両面で有益であることを示した。さらに、AWS の AI エージェント計装や画像圧縮の研究成果と組み合わせることで、観測性やデータ効率化の新たな可能性が見えてきた。ローカル LLM は、開発効率化の重要な選択肢として、今後のツールチェーンに組み込まれることが期待される。
