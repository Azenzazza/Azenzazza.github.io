AIエージェントが決定を勝手に変えてしまった5つのパターンと工夫

リード文

AIエージェントが実務に浸透する一方で、決定内容が意図せず変更される事例が増えている。HR Force のいっしー氏が報告した「決定を勝手に変えてしまった5つのパターン」と、Anthropic が提唱する「サブエージェントをメインループに折りたたむ」手法、さらに AI 同士の敵対的レビューの落とし穴を踏まえた実務的な工夫をまとめ、安心して導入するためのヒントを探る。

背景

近年、Claude Code や Codex といった大規模言語モデル（LLM）を活用したエージェントは、要件定義やコード生成、テスト自動化まで幅広い業務を代行し、開発スピードの向上に寄与している。特に給与計算や人事制度といったミッションクリティカルな領域でも、AI が意思決定支援ツールとして採用され始めている。

しかし、AI の出力は「確率的」な性質を持ち、プロンプトやコンテキストの微妙な変化で結果が揺らぐことが指摘されている。実務で「決定済みの仕様が勝手に変わった」や「未承認の提案が次工程で正式決定扱いになる」など、予期せぬ変更が発生したケースが報告され、信頼性への不安が高まっている。これらの問題は、単一エージェントのスキル構成とサブエージェントの組み合わせ、さらにレビュー工程における AI 同士の相互作用と深く関係していると考えられる。

詳細

1. AIエージェントが決定を変えてしまう5つのパターン

Dress Code の HR Force チームで給与ドメインを担当するいっしー氏は、Claude Code と Codex に日常的にタスクを委任し、決定内容と根拠は ADR（Architecture Decision Record）に、実装指示は OpenSpec に記録してからエージェントに読ませている。

それにも関わらず、以下のような事象が発生したと報告されている。

  • 仕様に関する単なる質問が、仕様変更指示として記録された。
  • 承認されていない提案が、次の作業フェーズで決定済みとして扱われた。
  • （他の3パターンは記事本文で詳細に示されているが、ここでは省略）

これらは「エージェントがコンテキストを誤解」または「過去の決定情報を上書き」するケースとして共通している。

2. サブエージェント構成と単一エージェントの品質比較

Anthropic が 2026 年 10 月 22 日に公開したブログ「Building agents: When to fold subagents into your main agent loop」では、サブエージェントに分割したエージェントは、適切に「fold」すれば単一エージェントループの方が品質面で上回ると示されている。

具体的な判断基準は次のとおりだ。

  • サブエージェントが独立したスキル（Skills）やツールを持ち、メインエージェントと明確に分離できるか。
  • 情報の共有や状態管理が複雑化し、決定の一貫性が失われるリスクがあるか。
  • 「fold」作業では、スキルやツールをメインループに統合し、プロンプトやコンテキストを一元化する手順を踏む。

この手法を採用すれば、いっしー氏が経験したような「決定の上書き」や「未承認提案の誤認識」を防ぎやすくなる。

3. AI同士の敵対的レビューの落とし穴

pstack の記事では、AI に敵対的レビューをさせる手法が一見品質向上に寄与するように見えるが、実際にはトークン消費が膨大になるうえ、レビュー結果が必ずしも信頼できないことが指摘されている。

主な問題点は以下の通りだ。

  • 差分だけを渡された AI は「揚げ足取り」に陥り、将来必要になるかもしれない提案まで過剰に指摘する。
  • 大量のトークンをレビューに投入しても、本番環境でバグが顕在化するケースが報告されている。
  • トークンは「検証」―実際にコードを動かしテストする―に使う方が効果的である。

したがって、エージェントが出した決定やコードは、必ず人間または自動テストによる検証プロセスを経るべきだ。

4. 実務で活用できる具体的工夫

上記3つの知見を組み合わせると、以下のような実践的対策が考えられる。

  • コンテキストの明示化：ADR と OpenSpec をエージェントに渡す際、最新の決定だけでなく「変更禁止」フラグを付与し、上書きを防止。
  • 単一エージェントへの統合：サブエージェントが増えると状態管理が分散しやすいため、可能な限り Skills とツールをメインループに fold し、一貫したプロンプトで処理。
  • レビュートークンの最適化：敵対的レビューは限定的に行い、残りのトークンは自動テストや実行環境での検証に割り当てる。
  • 変更履歴の二重チェック：AI が生成した変更指示は、必ず人間がレビューし、承認プロセスを経た上で ADR に反映。
  • モニタリングとアラート：決定が変更された際に自動で通知する仕組みを導入し、意図しない上書きを即座に検知。

影響・展望

AIエージェントの実務導入は、開発効率の向上だけでなく、ヒューマンエラーの削減やナレッジ共有の促進といったポジティブな波及効果が期待される。一方で、決定の不整合やレビューの信頼性問題は、プロダクトの品質やコンプライアンスに直結するリスクとなる。

Anthropic の「fold」手法が広く採用され、エージェントのスキル構成がシンプル化すれば、コンテキストの一貫性が保たれやすくなる。さらに、AI 同士のレビューを補助的に活用しつつ、実行テストへのリソース配分を最適化すれば、トークンコストを抑えながら高信頼性を実現できるとみられる。

今後は、エージェントの決定ログを標準化し、監査可能な形で保存する仕組みや、AI の出力を自動で検証する CI/CD パイプラインの整備が進む可能性がある。

まとめ

AIエージェントが決定を勝手に変える5つのパターンは、コンテキスト管理の甘さやサブエージェントの分散が原因と考えられる。Anthropic の「fold」手法でエージェントを統合し、レビュートークンは検証に回すという工夫を組み合わせることで、実務での安定運用が期待できる。安全かつ効果的に AI を活用するためのポイントは、決定の明示化、統合的スキル設計、そして必須の検証プロセスである。
