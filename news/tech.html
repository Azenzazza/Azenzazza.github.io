API キーはどこから漏れるのか？

リード文

AI エージェントの活用が急速に拡大する中、開発者は「API キー」をどのようにエージェントに渡すべきか悩んでいる。実際にキーが漏れるケースは、悪意ある攻撃者だけでなく、設定ミスや公開手順の不備からも多発している。本稿では、AI エージェントへのキー渡し方と、実際に観測された 1,566 件の .env アクセスから見える 7 つの漏洩経路を照らし合わせ、即実行可能な対策を提示する。

背景

2026 年 9 月下旬以降、大手企業での不正アクセスや情報漏洩が急増し、サイバー攻撃への警戒が高まっている。特に、開発現場で広く利用される AI コーディングアシスタント（Claude Code、Codex、Gemini CLI、Copilot、Cursor など）に対し、開発者が API キーを渡す方法が問われている。キーを対話文に貼り付ける、.env ファイルに記載してエージェントに読ませる、シェルの環境変数に設定する、MCP（Managed Credential Provider）や OAuth で委任するなど、手法は多様だが、渡し方によってはキーが意図せず外部に露出するリスクがある。

一方、Qiita に投稿された「API キーはどこから漏れるのか？」という実証記事では、同サイトに寄せられた 1,566 件の .env 探しリクエストを分析し、キー漏洩の実態を 7 つの経路に分類している。これらの経路は「リポジトリの公開」「ドキュメントの誤掲載」「CI/CD のログ出力」「開発者ツールの共有」「サードパーティサービスの設定ミス」「ブラウザのキャッシュ」「不適切な環境変数の公開」など、意外に身近な場所からも漏れることが示唆されている。

このように、AI エージェントへのキー渡しと、キーが実際に漏れる経路は密接に関連しており、開発フロー全体での管理体制が問われている。

詳細

AI エージェントへのキー渡し方とリスク

Qiita の実験記事では、以下の 6 つの渡し方を比較した。

  • 対話文に貼る：エージェントに直接キー文字列を入力する方式。対話履歴が保存されるプラットフォームでは、過去の会話が外部にエクスポートされる可能性がある。
  • .env ファイルに記載：ローカルの環境変数ファイルをエージェントに読ませる方式。ファイルが誤ってリポジトリにコミットされると、公開リポジトリ経由でキーが流出する。
  • シェル環境変数（.zshrc 等）に設定：プロセス起動時にキーが注入されるが、環境変数はプロセスリストやログに残るリスクがある。
  • MCP（Managed Credential Provider）：クラウドベンダーが提供する認証情報管理サービスを経由する方式。設定ミスがあると、エージェントが過剰な権限を取得できる。
  • OAuth：ユーザー認可フローでトークンを取得し、エージェントに渡す方式。トークンの有効期限やスコープ管理が不十分だと、長期的な漏洩につながる。
  • その他（例：コードスニペットに埋め込む）：一時的にコード内にキーを書き込むが、コードレビューや CI のログに残りやすい。

これらのうち、対話文や .env、環境変数は「可視化しやすい」ため、開発者が意図せず外部に露出させやすいとみられる。

実際に観測された 7 つの漏洩経路

「API キーはどこから漏れるのか？」の記事では、1,566 件の .env 探しリクエストを元に、以下の 7 つの経路に分類した。

  • リポジトリの公開：GitHub や GitLab で .env がコミットされ、クローラーに取得される。
  • ドキュメントの誤掲載：README や API 仕様書にキーが記載されたまま公開される。
  • CI/CD のログ出力：ビルドやデプロイ時に環境変数がログに出力され、ログ保存先で漏洩。
  • 開発者ツールの共有：VS Code の設定や拡張機能が共有フォルダに含まれ、キーが流出。
  • サードパーティサービスの設定ミス：外部サービスの API 設定画面でキーが誤って公開。
  • ブラウザのキャッシュ：開発用ローカルサーバーのレスポンスにキーが含まれ、キャッシュに残る。
  • 不適切な環境変数の公開：環境変数をそのまま HTTP ヘッダーやレスポンスボディに出力。

これらはすべて、キーを「どこかに置く」行為が起点となっている。特に .env ファイルは、対話文でエージェントに見せるケースと同様に、意図せず外部に露出しやすい点が共通している。

実践的な対策まとめ

上記リスクを踏まえ、Qiita の「基本対策を見直そう」でも推奨されている対策と合わせて、以下の手順が即実行可能である。

  • キーは決して平文でコードやドキュメントに埋め込まない。.env は .gitignore に必ず追加し、リポジトリ外で管理する。
  • AI エージェントには OAuth または MCP を利用し、最小権限・短時間有効なトークンで委任する。
  • CI/CD の設定で環境変数がログに出力されないよう、マスク機能を有効化する。
  • 開発ツール（VS Code 等）の設定ファイルは共有フォルダに置かず、個人ディレクトリで管理し、キーが含まれないことを確認する。
  • 外部サービスの API キー設定画面は定期的にレビューし、不要なキーは即削除する。
  • ブラウザキャッシュやサーバーレスポンスに環境変数が混入しないよう、ヘッダー出力を制御する。

これらを組み合わせることで、AI エージェントへの安全なキー渡しと、実際に起こり得る漏洩経路の双方をカバーできる。

影響・展望

AI エージェントが開発プロセスの一部として定着すれば、キー管理のミスはプロジェクト全体のセキュリティリスクに直結する。特に、2026 年以降に増加したサイバー攻撃の傾向は、キー漏洩が足掛かりになるケースが多いとみられる。したがって、組織は「キーの渡し方」だけでなく、漏洩経路全体を俯瞰したガバナンス体制を整備する必要がある。

今後は、AI エージェント側でも「安全なシークレット注入」機能が標準化される可能性がある。例えば、エージェントが直接環境変数を取得し、対話履歴に保存しない設計や、OAuth の自動リフレッシュ機能が組み込まれることが期待される。開発者側も、ツールチェーン全体で「キーはコード外部に保持」する原則を徹底すれば、漏洩リスクは大幅に低減できるだろう。

まとめ

AI エージェントへの API キー渡しは便利だが、対話文や .env への直接記載は漏洩リスクを高める。実際に 1,566 件の .env アクセスから明らかになった 7 つの漏洩経路と照らし合わせ、OAuth・MCP の活用、CI/CD ログのマスク、リポジトリの .gitignore 設定など、即実行できる対策を講じることが重要である。これにより、急増するサイバー攻撃下でも安全に AI エージェントを活用できる環境が構築できる。
